# Database schema

Alembic manages 14 domain tables in the current schema. The migration history records concrete schema changes:

| Revision | Schema change |
| --- | --- |
| `0001` | Creates the original 13 domain tables and enables pgvector. |
| `0002` | Adds durable queue, lease and provider metadata. |
| `0003` | Adds `agent_runs.recovery_attempt_count` and a unique approval-per-run constraint. |
| `0004` | Adds evaluation batches and extends evaluation results, bringing the domain total to 14 tables. |
| `0005` | Pins each batch to its evaluator version, preserving v1 history and defaulting new batches to v2. |

Policy retrieval uses the existing knowledge tables. LangGraph manages its checkpoint tables separately from these domain migrations.

## Identity, time, and storage conventions

Every table has an `id` primary key. Employee IDs are directory identifiers such as `EMP001` (`varchar(32)`); other IDs are UUIDs generated by the application. Normal records use UUIDv4, while demo seed records use deterministic UUIDv5 IDs. UUID columns have no database-generated default.

Timestamp columns use PostgreSQL `timestamptz`; application-generated timestamps are UTC. `created_at` and `updated_at` also have database `now()` defaults. SQLAlchemy updates `updated_at` during ORM updates; there is no database update trigger. JSON columns use JSONB in PostgreSQL. Enum values are stored as strings with database CHECK constraints rather than PostgreSQL native enum types.

SQLite supports isolated tests through portable column variants. It uses JSON for embeddings and does not validate PostgreSQL vector search behavior.

## Audit retention and approval boundaries

Foreign keys use `ON DELETE RESTRICT` except for ticket messages and policy chunks, which use `CASCADE`. A ticket with an agent run cannot be deleted while that run references it. Runs referenced by steps, tools, approvals, or evaluation results are likewise protected from parent deletion. This protects connected history; it does not make audit rows immutable against direct database edits or deletion in dependency order.

Approval identity is explicit: `(run_id, ticket_id, employee_id, repository_id, permission)` describes the proposed action; `approver_id` identifies the assigned reviewer and `decided_by_id` records the actual reviewer. The database enforces one approval per run, valid references, and complete decision audit fields. The approval service validates matching scope, current reviewer eligibility, and no self-approval. It locks the run/ticket/approval and commits the permanent decision together with resumable queue state. Same-decision retries preserve the first audit record; conflicts cannot overwrite it. The access tool rechecks approval and policy immediately before mutation.

Step summaries, details, policy evidence, and run state are intended for observable actions and concise decision summaries. Private model chain-of-thought must not be written to these fields.

## Policy sources and retrieval

The initial migration enables the PostgreSQL `vector` extension. The seed command indexes eight source documents into 35 section chunks using the configured embedding provider. Changed source documents and their replacement embeddings commit together. `python -m app.rag.ingest` atomically reindexes existing sources and skips unchanged complete documents. `--force` regenerates every embedding. Failed indexing preserves the prior committed corpus.

Each chunk has a 1536-dimensional embedding, provider/model identifiers, and metadata containing `document_hash`, `version`, `section`, `chunk_hash`, and `chunker_version`. PostgreSQL executes cosine distance ranking with top-k and optional document filters. Retrieval validates the complete corpus and rejects missing sections, stale source/metadata, malformed vectors, or mixed models. Exact search is used; no approximate index is needed for 35 chunks. SQLite computes cosine locally solely for offline tests.

Changing provider/model requires re-embedding; changing dimensions also requires a schema migration. Run traces snapshot source/chunk IDs, title, version, section, excerpt, cosine score, and document hash. Reindexing can replace chunk IDs without erasing past trace evidence. Run JSON stores `workflow_version` and the selected `retrieval_config`; older workflow-version-1 runs retain their original graph routing. Supported policy content is independently bound to the committed authorization manifest, so indexing changed text cannot silently change the deterministic rules.

## LangGraph persistence

`agent_runs.state` is a domain-visible execution snapshot and `graph_thread_id` links it to an actual LangGraph thread. Native checkpoint storage is separate from the 14 domain tables. `PostgresSaver.setup()` creates and migrates its own tables (`checkpoint_migrations`, `checkpoints`, `checkpoint_blobs`, and `checkpoint_writes`) in the configured `CHECKPOINT_SCHEMA`, default `resolveai_checkpoints`. The database role must be able to create that schema and its tables. Alembic manages the domain schema; it does not own the checkpointer's internal versioning.

Checkpoint initialization occurs when a worker opens its store. Operators may initialize it explicitly with `python -m app.agents.checkpoints` from `backend/`. SQLite tests use a separate `CHECKPOINT_SQLITE_PATH`; that file is not part of the deployment architecture.

Run submission persists queue state before returning `202`. The worker claims pending or expired runs, checks lease ownership before writes, and recovers the same graph thread. Completed step deltas and cached tool results prevent repeated effects when a domain commit precedes checkpoint persistence. Tool idempotency keys cannot be reused with different arguments. Workflow version `3` uses a native durable interrupt; only after that checkpoint exists does the worker set run and ticket to `WAITING_FOR_APPROVAL` and release the lease. A decision sets the run to `PENDING`, ticket to `PROCESSING`, and resets `recovery_attempt_count`. Total `attempt_count` includes both claims and resumes; bounded recovery uses the separate counter within each execution segment. Historical versions retain their original routing.

The grant and its tool-result record commit together. Verification uses another tool execution and step. The close tool validates that completed verification trace and rereads current permission before setting `RESOLVED`, `resolved_at`, and the final assistant message in one transaction. Bearer sessions are stateless signed tokens; no additional session table or authentication provider is introduced.
